# Part A — Localization Decision Record

## A1. Requirements (from the contract and the existing site)

| Requirement | Source |
| --- | --- |
| Four locales: `en`, `es`, `pt`, `fr`; default `en`; prefix routes; trailing slash | `src/i18n/config.ts`; `astro.config.mjs` |
| No English fallback for article content | ARK-BLOG-002 §5; existing README i18n section |
| Each locale publishable independently | ARK-BLOG-002 §5 item 3 |
| Missing translation creates no route, hreflang, sitemap or RSS entry | ARK-BLOG-002 §5 |
| Localised slug per locale, not misleading | ARK-BLOG-002 §5 |
| Astro obtains published alternates for hreflang | ARK-BLOG-002 §5; ARK-BLOG-006 |

## A2. Verified Storyblok facts that drive the decision

- Field-level translation applies to all field types **except Blocks and Groups** (Fields page).
- Publishing all languages together is the **default**; individual language publishing is **opt-in**, under Settings → Internationalization (Internationalization page).
- Translated slugs and Dimensions are apps, described as plan-dependent (Internationalization page).
- The API takes a `language` parameter with codes such as `es`; fallback is available via `fallback_lang` but its behaviour for untranslated content is **not documented** (Astro i18n quickstart).
- hreflang is **not** generated by Storyblok.

## A3. Options

| Option | Description | Strengths | Weaknesses |
| --- | --- | --- | --- |
| **L1.** Field-level translation in one story per insight | One `insight` story; all locales in its translatable fields; per-language publish state. | One identity; one place to edit; no duplicate structure; matches the "one conceptual publication" rule. | Requires per-language publishing (plan). Blocks cannot be translated, so the body must be Rich text. Per-locale status through the API is unverified (R-01). |
| **L2.** Separate story per locale, linked by a shared key | One `insight` story per locale; a shared `translation_key` field groups them. | Each story publishes independently with no plan dependency for publication. Clear status per locale. | Editors maintain four stories per article. Drift risk between versions. Relations must go through the key, not the story identity. |
| **L3.** Hybrid (L1 for most fields, L2 for body) | Mixed. | None that justify the complexity. | Rejected. Complexity without requirement. |
| **L4.** Separate spaces per locale | One space per language. | Strong isolation. | Operationally heavy; cross-locale relations are harder. Not justified for four locales of a single site. Rejected. |

## A4. Evaluation against the requirements

| Requirement | L1 | L2 |
| --- | --- | --- |
| One conceptual article | Natural | Via `translation_key` |
| Independent publication per locale | Requires per-language publishing (plan) | Native |
| No English fallback | Requires that the app detects untranslated content (R-01) | Native: missing story means no version |
| Localised slug per locale | Localised `slug` field (recommended) | Story slug per locale, or localised `slug` field |
| Body without Blocks | Rich text field | Rich text field |
| hreflang from published alternates | Needs per-locale status (R-01) | Group by `translation_key`; each story's status is its own |
| Editor effort | Lower | Higher |
| Plan dependency | Yes (per-language publishing) | No, for publication |

## A5. Recommendation (conditional)

1. **If the owner's plan supports per-language publishing and the spike confirms per-locale status (R-01):** adopt **L1**.
   - One `insight` story per article.
   - Translatable fields: `title`, `excerpt`, `slug`, `body`, `cover_alt`, `seo_title`, `seo_description`, `author_role`, `author_bio`, `cta_label`.
   - Shared fields: `format`, `publication_date`, `featured`, `cover_image`, `category`, `services`, `offerings`, `cta_service`, `related_insights`, `seo_noindex`, `seo_image`, `author_name`, `author_linkedin`.
   - Blocks are not used; the body is Rich text.
2. **If per-language publishing is not available (R-04):** adopt **L2**.
   - One `insight` story per locale, sharing `translation_key` (a stable text key, shared across the four stories).
   - All fields are non-translatable in each story (each story is its own language).
   - Astro groups stories by `translation_key`. An article exists in locale X only if its story in locale X is published and eligible.
   - Related insights reference the story of the same locale, found through `translation_key`.

**Do not** use `fallback_lang` in either option. **Do not** merge the two options in one space.

## A6. Slug strategy

- **Public slug:** a localised text field `slug` per locale (both L1 and L2). This keeps URLs deterministic in the application and avoids the plan-dependent Translated Slugs app.
- **Internal story slug:** a stable key (for example `ins-0001-…`), never public, used only for the Storyblok path.
- **Uniqueness:** Astro build fails if two eligible insights in the same locale share a public slug. Storyblok cannot enforce this across stories in the verified documentation.
- **Immutability:** a published slug must not change without a redirect procedure. Redirect design is deferred to ARK-BLOG-004.
- **Translation not ready:** an empty or missing localised slug means no route in that locale. Never derive it from another locale's slug.

## A7. Publication rules by locale

| Situation | Public result |
| --- | --- |
| Locale X published and all required fields present | Route, archive entry, teaser entry (if within count), sitemap, RSS item, hreflang alternate |
| Locale X published but a required field missing | No route in X; logged at build; no hreflang alternate to X |
| Locale X unpublished, locale Y published | No route in X; hreflang only for Y |
| Locale X draft only | Never public |
| No locale published | Insight absent from all public output |

## A8. hreflang and canonical rules

- Each public page has a **self-referencing canonical** (existing behaviour in `BaseLayout.astro`).
- hreflang alternates are emitted **only** for locales whose version is eligible (§A7).
- `x-default` points to `en` **only if** the `en` version is eligible. If not, the existing helper must not emit `x-default` to a missing page. **Gap:** the current `xDefaultPath` helper must be checked in ARK-BLOG-006.
- The sitemap and RSS include only eligible versions. The `seoSitemap` hook in `astro.config.mjs` reads `hreflang` from HTML, so it inherits the rule automatically.

## A9. Operational trade-offs for editors

| Topic | L1 | L2 |
| --- | --- | --- |
| Writing a new article | Write once, translate fields in place | Create four stories and keep the key aligned |
| Updating a published article | Edit the locale field; publish that language if individual publishing is enabled | Edit each locale story separately |
| Missing translation | Shown as "not published in this language" in the editor (verify) | Visible as a missing story |
| Risk of drift | Low | Medium: owners must update all versions |
| Training | Field-level translation and per-language publish | Story naming and the `translation_key` |

# Part B — Homepage Insights Teaser Contract

## B1. Purpose

Show the latest eligible published insights on the corporate homepage with a localised link to the archive. The teaser must not require a second content model or a hand-maintained list (ARK-BLOG-002 §4.7; contract requirement).

## B2. Eligibility

An insight is eligible for the teaser in locale X when it meets the rules in `ark-blog-002-v2-content-model.md` §5.7 **and**:

- its `publication_date` is at or before the build time;
- it is not marked `seo_noindex` **only** if the owner decides noindex also excludes it from listings (decision TZ-3; default: noindex does not exclude from teaser).

Drafts, unpublished locales and invalid records are excluded.

## B3. Sorting

- **Primary:** `publication_date`, descending.
- **Tie-breaker:** public `slug`, ascending.
- **Not used:** `featured`, `updatedAt`, or Storyblok system timestamps.

**Conflict with the existing code.** `src/lib/insights/normalize.ts` sorts featured articles first, then by date. That order would place an older featured article above newer ones, contrary to "most recent". **Change required** in ARK-BLOG-004/005. The featured flag is moved to the archive highlight (content model §6.1).

## B4. Count

- Default **3** items, to match the current three-card layout.
- Configurable within **3–4** by a single constant. The range is fixed by the contract.

## B5. Locale-aware retrieval

- One retrieval per locale at build time.
- Fetch a candidate window larger than the count (recommended: up to 12) so that eligibility filtering can still fill the teaser.
- Filter in Astro with the rules in §B2 and the content model §5.7.
- Never request a locale and silently display another locale's content.

## B6. Fewer than the target count

| Eligible in locale X | Behaviour |
| --- | --- |
| ≥ count | Show `count` items. |
| 1 to count − 1 | Show the available items. Do not pad with other locales or with placeholders. |
| 0 | See B7. |

## B7. Empty state

Two options. The current code shows the "Próximamente" card (restored by the owner in this session).

| Option | Behaviour | Verdict |
| --- | --- | --- |
| E1. Keep "Próximamente" | Shows a holding card. | **Default until the owner decides.** Matches the current owner-approved state. |
| E2. Hide the section | Section does not render. | Preferable once content exists and the empty state is no longer intended. Owner decision (TZ-4). |

## B8. "View more" destination

- Destination: `/{locale}/insights/` (the archive for the active locale). Existing helper: `insightsPath(locale)`.
- Label: localised. **Copy decision required.** Current labels: "View all insights", "Ver todos los artículos", "Voir tous les articles", "Ver todos os artigos". The contract asks for "View more" / "Ver más".
- **Proposed** wording (not yet approved): EN "View more", ES "Ver más", FR "Voir plus", PT "Ver mais".

## B9. Dynamic vs curated

| Mode | Behaviour | Trade-off | Verdict |
| --- | --- | --- | --- |
| Dynamic | Latest eligible items at build time. | No maintenance; always current after a rebuild. | **Recommended default.** |
| Curated | Editor selects teaser items through references. | Editorial control; a second list to maintain; can show stale or unpublished selections. | Only if the owner requires explicit placement. Then a teaser field on the homepage, not a separate content type. |

## B10. Failure behaviour

Static output means a failed retrieval affects the **deployed** page, not the reader's view at request time.

| Case | Behaviour | Note |
| --- | --- | --- |
| Storyblok returns a valid response with zero eligible items | Empty state (B7). | Normal case. |
| Storyblok unreachable or error response | **Conflict.** Options below. | Owner decision (TZ-1). |
| Partial response (for example some locales missing) | Log a build warning per locale. Do not show content from another locale. | Recommended. |

**Options for an unreachable CMS:**

| Option | Behaviour | Trade-off |
| --- | --- | --- |
| F1. Fail the build (current behaviour of the removed Hygraph client) | No deployment; the previous deployment stays live. | Protects against publishing an empty teaser or stale content. Corporate sections are not updated until the CMS returns. |
| F2. Degrade the teaser only | Build continues; teaser shows the empty state. | Keeps other sections deployable. Risk: a deployment during an outage publishes an empty teaser. |

**Recommendation:** F1 for the build, because the static model has no other way to avoid publishing an empty teaser. This conflicts with the contract wording "must not break unrelated corporate sections". The owner must decide (TZ-1). If F2 is chosen, the build must emit a visible warning and keep the last successful teaser data where the host allows it.

## B11. Shared data path

- The teaser and the archive use the **same** eligibility function and the same per-locale data path (`getInsights(locale)` or its successor). No second CMS integration.
- The homepage calls the function with `count` only; the archive calls it without a limit.

## B12. Navigation consistency

- Header: Insights → `/#insights` (owner decision in this session). Scrolls to the teaser.
- Footer: Insights → `/{locale}/insights/`. The footer currently shows the link even with no articles (`PageLayout.astro` passes the link unconditionally). **Recommended:** show the footer link only when the locale has at least one eligible insight (decision TZ-5).
